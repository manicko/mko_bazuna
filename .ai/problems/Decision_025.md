# Задача: Исследование и спецификация фильтров и сортировок каталога

## Цель

Подготовить спецификацию системы фильтрации и сортировки объявлений с учетом специфики основных категорий сайта.

Необходимо исследовать, как аналогичный функционал реализован на крупных досках объявлений и маркетплейсах, определить наиболее полезные и распространенные фильтры для каждой категории  и на основании исследования разработать единый подход к реализации фильтров в нашем проекте.

Основные ориентиры для исследования:

- Avito
- OLX (в первую очередь OLX Казахстан, а также другие региональные версии при необходимости)
- другие крупные сайты объявлений/маркетплейсы, если они имеют релевантный функционал.

---

## 1. Анализ существующих категорий

Для каждой основной категории нашего сайта провести отдельный анализ.

Основные категории: взять текущий список


При необходимости анализировать также подкатегории второго/третьего уровня, поскольку набор фильтров может существенно различаться внутри одной основной категории.

Например, для недвижимости отдельно рассмотреть:

- квартиры;
- дома;
- гаражи;
- коммерческая недвижимость;
- земельные участки;

и т.д.

---

## 2. Исследование конкурентов

Для каждой рассматриваемой категории изучить:

### Фильтры

Определить:

- какие фильтры используются;
- к какой сущности/характеристике относится фильтр;
- тип фильтра:
  - диапазон;
  - checkbox;
  - radio;
  - select;
  - multi-select;
  - boolean;
  - текстовый;
  - числовой;
  - дата и т.д.;
- является ли фильтр обязательным или дополнительным;
- зависит ли он от выбранной категории;
- зависит ли он от других фильтров;
- используется ли поиск по этому параметру;
- используется ли параметр только как фильтр или также отображается в карточке объявления.

### Для каждого фильтра зафиксировать

Пример:

| Категория | Параметр | Тип | Значения/диапазон | Зависимость | Avito | OLX |
|---|---|---|---|---|---|---|
| Квартиры | Площадь | range | м² | квартира | ✓ | ✓ |
| Квартиры | Количество комнат | multi-select | 1,2,3,4... | квартира | ✓ | ✓ |
| Квартиры | Этаж | range | 1...N | квартира | ✓ | ✓ |
| Квартиры | Ремонт | select | ... | квартира | ✓ | ✓ |

Необходимо не просто перечислить фильтры, а определить **назначение и практическую ценность** каждого параметра.

## 3. Анализ сортировок

Для каждой категории определить доступные варианты сортировки.

Исследовать:

- по цене;
- по дате публикации;
- по релевантности;
- по популярности;
- по расстоянию;
- другие варианты.

Для каждой сортировки определить:

- используется ли она;
- является ли сортировка универсальной или зависит от категории;
- направление сортировки (ASC/DESC);
- имеет ли она смысл для нашего проекта.

Отдельно определить минимальный набор сортировок для MVP.

## 4. Сравнение категорий

После анализа составить матрицу:

```text
Категория → набор фильтров
````

Определить:

### Группы категорий с одинаковыми фильтрами

Например:

```text
Квартиры
Дома
Таунхаусы
```

могут использовать общий набор:

```text
Цена
Площадь
Количество комнат
Количество этажей
Состояние
...
```

### Категории с частично совпадающими фильтрами

Например:

```text
Квартиры
Дома
```

имеют общие параметры, но дома дополнительно имеют:

```text
Площадь участка
Количество этажей
...
```

### Уникальные категории

Определить категории, которым требуется полностью отдельный набор фильтров.

## 6. Зависимости фильтров

Особое внимание уделить зависимым фильтрам.

Например:

```text
Категория: Автомобили
        ↓
Марка: BMW
        ↓
Модель:
  X5
  X3
  3 Series
```

или:

```text
Недвижимость
    ↓
Тип объекта: Квартира
    ↓
Количество комнат
    ↓
Тип сделки
```

Определить:

* какие фильтры появляются только после выбора определенной категории;
* какие значения фильтра зависят от другого фильтра;
* какие фильтры должны динамически изменять доступные значения.

## 7. Определение MVP

На основании исследования определить:

### Обязательные фильтры MVP

Фильтры, которые необходимо реализовать на первом этапе.

### Желательные

Полезные, но не критичные для запуска.

### Deferred

Фильтры, которые сейчас не нужны и могут быть добавлены позже.

Для каждого deferred-фильтра указать причину отложить его.

---

## 8. Предлагаемая архитектура фильтров

На основании исследования предложить, как реализовать фильтры в нашем проекте.

Необходимо определить:

* где хранится описание фильтра;
* где хранится набор допустимых значений;
* как фильтр связывается с категорией;
* как задаются зависимости между фильтрами;
* как реализуется порядок отображения фильтров;
* как определяется тип UI-компонента;
* как фильтры передаются через URL;
* как фильтры применяются в PostgreSQL/Django ORM;
* как обеспечить возможность добавления новых фильтров без изменения большого количества существующего кода.

Отдельно определить, какие параметры должны быть обычными полями модели `Ad`, а какие могут быть реализованы через существующую систему `LookupGroup / LookupItem` или другую структуру.

---

## 9. Производительность

Предложить подход с учетом того, что:

* основная БД — PostgreSQL;
* поиск должен быть быстрым;
* фильтрация является одной из ключевых функций сайта;
* проект должен поддерживать дальнейшее увеличение количества объявлений.

Определить:

* какие поля необходимо индексировать;
* какие фильтры могут использовать обычные B-tree индексы;
* где нужны составные индексы;
* какие параметры могут использовать PostgreSQL-specific возможности;
* какие фильтры потенциально могут стать проблемными при росте количества объявлений.

Не заниматься преждевременной оптимизацией — решение должно соответствовать текущему масштабу проекта, но не создавать архитектурный тупик.

## 10. URL и состояние фильтров

Определить единый формат URL для фильтров.

Например:

```text
/search/?q=iphone&city=podgorica&price_min=100&price_max=500
```

Для категорий:

```text
/search/?category=phones&brand=apple&condition=used
```

URL должен:

* быть воспроизводимым;
* позволять поделиться результатами поиска ссылкой;
* корректно работать после перезагрузки страницы;
* позволять использовать Back/Forward браузера;
* быть совместимым с HTMX-интерфейсом;
* не содержать лишнего внутреннего состояния приложения.

## Главный принцип

Не копировать фильтры конкурентов один в один.

Цель исследования — определить:

1. какие фильтры действительно нужны пользователю;
2. какие фильтры являются общими;
3. какие зависят от категории;
4. какие можно реализовать единым механизмом;
5. какие стоит отложить;
6. как построить систему, которую можно расширять добавлением новых категорий и фильтров без существенной переработки существующего кода.
