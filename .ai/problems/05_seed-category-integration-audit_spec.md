## 1. Problem Statement

Three sequential development efforts — demo seed data, content fixtures, and category lookup architecture — were implemented in independent tracks. After all three were completed, the seed data module and the new category architecture are **not integrated**. The seed module continues to use old category slugs, fixture files, and photo manifests that are incompatible with the new canonical `categories.yaml` category system.

This results in the following concrete failures:

1. **Broken photo generation**: `photo_manifest.json` is an empty stub (75 bytes, `categories: {}`). `ImageGenerator.generate()` loads zero photos and returns an empty list. Ads get zero images despite 28 JPEG files on disk.
2. **Category slug mismatch**: `ads_templates.json` (67 template entries) exclusively uses old Russian slugs (`kvartiry`, `avtomobili`, `foto`, etc.) that do not exist in the new `categories.yaml` system (which uses English slugs like `apartments`, `cars`, `cameras`, etc.).
3. **Orphaned photo files**: 28 JPEGs in `seed/fixtures/images/` are named with old slugs and have no manifest entries — they are invisible to the seed system.
4. **Stale `query_hierarchy.json`**: This file drives the `download_seed_photos.py` script but uses old slugs. The download script cannot produce photos for the new category system.
5. **Hardcoded old slugs in `AdGenerator`**: `CATEGORY_GROUP_MAP` and `_generate_price()` in `ads.py` reference old slugs that no longer match any category in the database.
6. **Tests use old slugs**: `test_seed.py` creates test categories with old slugs. Tests will fail against the new category system.
7. **Dead/orphan files**: `categories.json` old fixture, `query_hierarchy.json` mislocated, potentially other artifacts.
8. **No documentation**: No instructions exist for running seed scripts, photo downloads, or the content generation pipeline.

**What is needed:** A systematic audit and remediation that brings the seed module into full compatibility with the new `categories.yaml` canonical category system, removes dead code, and documents the workflow.

## 5. Research Summary

### 5.1 Download Script Compatibility

**Finding:** `scripts/download_seed_photos.py` is **slug-agnostic** — it reads `query_hierarchy.json` keys and uses each key directly as `category_slug` for filenames and manifest entries. No code changes needed.

**Key details:**
- Filename format: `{category_slug}_{NN:02d}.jpg` (line 399)
- Manifest update: `update_manifest_for_category(manifest, category_slug, filename, width, height)` (line 417)
- `ImageGenerator` matches photos via `ad.category.slug` (line 137 in `images.py`)
- If `query_hierarchy.json` contains new slugs, the script produces correctly-named files and matching manifest

**Config changes needed:**
- `pexels_safe_limit` must be bumped from 150 to ≥800 (for 60 categories) or ≥2200 (for 171 categories)
- Unsplash is currently disabled (`unsplash: false`) — consider enabling as fallback

**Rate limit analysis:**
- 60 categories × 3 photos = 180 photos → ~540-720 search requests → ~5-8 minutes at Pexels free tier
- 171 categories × 3 photos = 513 photos → ~1,539-2,052 search requests → ~15-25 minutes

### 5.2 LLM Prompt Analysis

**Finding:** The current prompt at `.ai/llm-tasks/seed-content-generation.md` (183 lines) has several deficiencies:

1. **Inlines all 30 old slugs** in a dedicated section — must be replaced with YAML reference
2. **References `fixtures/categories.json`** as category source — must be updated to `categories.yaml`
3. **Omits `word_lists.json`** as explicit output — spec section 11.1 requires it but the prompt doesn't define it
4. **Single-session workflow** — 171 leaf categories requires splitting into 7 sessions

**Category count analysis:**
- Total categories in YAML: ~205
- Top-level sections: 7 (real-estate, transport, goods, animals, services-jobs, business, charity)
- Leaf categories: 171
- Templates needed: 342+ (2 per leaf) + 4 default = 346+
- Per-session estimate: ~25 leaf categories, ~50 templates per session

**Recommended approach: Split into 7 LLM sessions, one per top-level section, then merge.**

### 5.3 Hardcoded Slug Locations in `ads.py`

**Critical finding:** `AdGenerator` has two code locations with hardcoded old slugs:

1. **`CATEGORY_GROUP_MAP`** (lines 25-38): Maps 13 old slug patterns → brand group identifiers
   - Example: `"elektronika": "elektronika"`, `"avtomobili": "avtomobili"`, `"kvartiry": "real_estate"`
   - Must be updated to map new slugs like `"cars": "vehicles"`, `"apartments": "real_estate"`

2. **`_generate_price()`** (lines 331-333): Special price ranges for old real estate and vehicle slugs
   - Must be updated to reference new real estate and vehicle slugs

**These are BLOCKERS** — without this fix, regenerated templates and photos will still not work at runtime.

### 5.4 Test Data Analysis

**Finding:** `test_seed.py` creates test categories with old slugs in multiple places:
- Test data setup creates categories like `nedvizhimost`, `avtomobili`, `elektronika`, `kvartiry`, `telefony`
- These must be updated to match new slugs from `categories.yaml`

## 6. Assumptions

1. `categories.yaml` at `apps/categories/catalog/categories.yaml` is the authoritative source for all category slugs and hierarchy.
2. The builder module (`categories/catalog/builder.py`) correctly creates Category records from the YAML, and the slugs in the database match the YAML.
3. The existing `download_seed_photos.py` script works without modification — only `query_hierarchy.json` and config need updating.
4. The LLM agent has web browsing capability and can read `categories.yaml` from the file system.
5. All 28 old JPEGs in `fixtures/images/` can be safely deleted (git-tracked, no other code references them by filename).
6. The `pexels_safe_limit` in `seed-images-config.json` can be bumped to accommodate the new category count.
7. The 4 `default` templates in `ads_templates.json` are slug-agnostic and can be preserved without changes.
8. No external code (outside the seed module) references the deleted `categories.json` fixture.

---

## 7. Constraints

1. **No runtime network dependency** — all photos must be bundled in the repo (per spec `02_demo-seed-data`, constraint N05).
2. **Zero budget** — only free CC0 photo sources (Unsplash, Pexels free tiers).
3. **Repo size** — total photo bundle must not exceed ~15MB (no Git LFS).
4. **All new code and documentation in English** (project rule 1).
5. **StrEnum for all new constants** (project rule 10).
6. **No `print()` in service layer** — use `logger` (project rule 12).
7. **LLM prompt must reference `categories.yaml`** — do not inline 171 category slugs.
8. **Photos must be ≤100KB each**, EXIF stripped, JPEG format, max 1080px on long side.

## 8. Risks

| Risk | Likelihood | Impact | Mitigation |
|------|-----------|--------|------------|
| Pexels API rate limit insufficient for 180+ photos | Medium | Medium | Bump `pexels_safe_limit` to ≥800. Enable Unsplash as fallback. Run in multiple passes with `--all`. |
| LLM context window too small for 171 categories | High | High | Split into 7 sessions (one per top-level section). Each session handles ~25 leaf categories. |
| LLM output quality poor for Bosnian (bs) localization | Medium | Medium | Include explicit instruction in prompt: "natural Bosnian, Latin script, Montenegro vocabulary." Human review spot-check. |
| `CATEGORY_GROUP_MAP` mapping misses edge cases | Medium | Medium | Design with sensible default group. Add tests that verify every category slug has a mapped group. |
| Downloaded photos exceed repo size limit | Low | Medium | Enforce 100KB per photo. Total 513 photos × 100KB = ~51MB — may exceed limit. Consider reducing to 60 most-common categories (180 photos × 100KB = ~18MB). |
| Old 28 JPEGs must be `git rm`'d (not just deleted) | Low | Low | Use `git rm src/backend/apps/seed/fixtures/images/*.jpg` to stage removal. |
| Merge step for 7 LLM sessions may introduce errors | Medium | Low | Add automated validation script that checks: all slugs valid, no duplicate IDs, JSON parseable. |

## 9. Open Questions

1. **Photo count per category:** Should all 171 leaf categories get 3 photos each (513 total, ~51MB), or should a subset of ~60 high-traffic categories get 3 photos each (180 total, ~18MB)? The repo size constraint favors the subset approach.
2. **LLM session merging:** Should the merge of 7 section files be done by a Python script, or by the LLM in a final pass?
3. **`pexels_safe_limit`:** What is the current Pexels account tier? (Standard: 200 req/hr, Verified: 20,000 req/hr). This determines whether the download completes in one session or needs multiple passes.
4. **`CATEGORY_GROUP_MAP` design:** Should the group mapping be hardcoded (as currently) or moved to a config/YAML file for future extensibility?

## 10. Out of Scope

- **Full refactoring of `AdGenerator`** — only the hardcoded slug references and price logic need updating. The generator architecture stays unchanged.
- **Web posting UI** — sellers post only via Telegram bot. No web posting changes.
- **Multi-currency support** — single BAM currency only (YAGNI).
- **Photo moderation pipeline** — seed photos are assumed appropriate.
- **AI image generation** — no AI-generated images at runtime. All photos are pre-bundled.
- **Dynamic category reloading** — categories are loaded at migration/seed time, not watched at runtime.
- **Category tree restructuring** — the `categories.yaml` structure is assumed correct. No changes to the tree itself.
- **`query_hierarchy.json` path relocation** — the file stays at `seed/fixtures/images/`. No path changes.
