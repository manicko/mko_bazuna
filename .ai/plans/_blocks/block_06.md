# Block 6: Sorting & Price Ordering

## 1. Block Summary

Verifies the four-way `AdSort` ordering (date_asc, date_desc, price_asc, price_desc) on the non-FTS listings/search paths, the `NULLS LAST` guarantee for price sorts on `price_normalized_eur`, the intentional hiding of the sort dropdown (and ignoring of `sort`) when an FTS `q` query is active, and the persistence of `sort` across pagination/chip URLs with fallback to `date_desc` on invalid input.

**Source:** `.ai/research/search-journeys-our-architecture.md` (Block 6), `.ai/problems/01_search_patterns_test_verification_top_plan.md:139-152` (key variations), `docs/01-spec/search-patterns.md:161-202`, `docs/01-spec/filter-ui.md:388-411`

## 3. Priority

**Medium.** Block 6 covers the core sort UX surface for both listings (`/`, `/category/<slug>/`, `/city/<slug>/`) and search (`/search/?q=`). No high-severity defects, but two variations carry Medium risk:

- **V1 (FTS-hidden-sort gap) is the highest concern** — it is *intentional* per spec (`search-patterns.md:161-163`) that FTS results ignore `sort` and always order by `-rank, -published_at, -id`, yet no test guards this contract. A future refactor that wires `sort` into the FTS branch (a plausible enhancement, explicitly flagged as an open product decision at `01_search_patterns_test_verification_top_plan.md:251`) would silently alter relevance ordering. The test must assert *current* behavior and be reviewed if product changes the decision.
- **V2 (price sort direction)** is **Medium** because neither listings nor search has a behavioral test asserting that `price_asc` = lowest-first and `price_desc` = highest-first. Only NULL-placement (V3) is guarded, and the existing `TestPriceNullSort` uses only 2 ads (one priced, one null) — insufficient to detect an asc/desc swap.
- **V3 (NULLS LAST on search)** is **Low** — listings path is fully covered (`test_catalog_filters.py:391-444`); the search path is a literal mirror (`search.py:204,206`) but should be covered to prevent drift.
- **V4 (sort persistence)** is **Low** — the `&sort={{ current_sort }}` strings are visible in template source, so a structural assertion is cheap and sufficient; the risk is a cosmetic UX regression (lost sort on page navigation).
- **V5 (invalid sort fallback)** is **Low** — edge-case input that already falls back to a safe default; the echo-in-URL deviation is noted but not actionable without a product decision.

## 5. Validator Recommendations

### 5.1 V1 — FTS-hidden-sort gap (Medium)

- **Behavioral (integration, `/search/?q=<term>&sort=price_asc`):** Use the `TestRelevanceTiebreaker` pattern (`test_catalog_filters.py:447-475`) — create two ads with the same title (identical FTS rank) but different prices and `published_at` 1s apart; assert `page_obj` ordering follows `published_at` (tiebreaker), NOT price. This proves `sort=price_asc` is ignored when `q` is active. Use a single-word query that triggers FTS but not fuzzy category match (to keep the ad set in the same category).
- **Template-source (no DB):** Read `filter_form.html`; assert the `<select name="sort"` block (`lines 104-124`) is wrapped in `{% if not query %}` (line 103) / `{% endif %}` (line 125). Assert the `<select name="sort"` substring does NOT appear in rendered HTML when `query` is truthy — render `/search/?q=<term>` with HTMX and `assert "name=\"sort\"" not in content`.
- **Spec reference:** `search-patterns.md:161-163` — "when a `q` full-text query is active, results rank by FTS relevance then `-published_at, -id`". The product decision flag at `01_search_patterns_test_verification_top_plan.md:251` must be re-evaluated if sort-on-FTS is ever enabled.

### 5.2 V2 — Price sort direction (Medium)

- **Integration:** Create 3+ ads with distinct non-null `price_normalized_eur` (e.g., 50, 150, 300) using `create_test_ad(..., price=N, status=AdStatus.PUBLISHED)` (`conftest.py:135`). Assert `/?sort=price_asc` → `page_obj` ordered [50, 150, 300] and `/?sort=price_desc` → [300, 150, 50] by price. Use `create_test_ads_bulk` (`conftest.py` import) for 3+ ads in one call, or the explicit-`published_at` pattern from `test_listings_sort.py:30-50`. Replicate on `/search/` (no query) using the `TestSearchViewSorting._make_ads` pattern (`test_search_triggers.py:199-215`).
- **Reuse:** Mirror the `TestListingsSortOrder` assertion style (`html.find("Alpha Ad")` position comparison) OR the `TestSearchViewSorting` style (`response.context["page_obj"]` title list) — keep consistent within each test class.

### 5.3 V3 — NULLS LAST on search (Low)

- **Integration:** Mirror `TestPriceNullSort` (`test_catalog_filters.py:391-444`) exactly but hit `/search/?sort=price_asc` and `/search/?sort=price_desc` (no `q`). Create one priced ad (`price=100`) and one null-price ad (`price=None`); assert both appear and `ids[-1] == null.id` on the search no-query path. The `price` kwarg to `create_test_ad` maps to `price_normalized_eur` via `PriceNormalizer` (`conftest.py:135,177`).

### 5.4 V4 — Sort persistence (Low)

- **Template-source (no DB):** Read `ad_list.html`; assert `content.count("&sort={{ current_sort }}")` == 9 (one per link, both `href` and `hx-get` pairs share the same expression so each appears twice per link → 18 total, or assert the substring appears in at least all 9 link blocks). Simpler: assert each of the 9 `hx-get=` lines (at `ad_list.html:42,54,65,72,143,147,157,165,169`) contains `&sort={{ current_sort }}`.
- **Integration:** GET `/?sort=price_asc` with 25+ ads (forces 2 pages) + HTMX header; assert the rendered "next page" link (`ad_list.html:164,165`) contains `sort=price_asc` in both `href` and `hx-get`. Reuse `create_test_ads_bulk(count=25, ...)` (`test_catalog_filters.py:549-555`).
- **Dropdown auto-submit:** Template-source no-DB: assert `filter_form.html` line 110 contains `onchange="this.form.requestSubmit()"` and that the `<form>` (`filter_form.html:5-10`) does NOT have an inline `onsubmit` that would double-submit.

### 5.5 V5 — Invalid sort fallback (Low)

- **Integration:** GET `/?sort=not_a_real_sort` and `/search/?sort=not_a_real_sort` (no query); assert `response.context["page_obj"]` ordering equals the default `date_desc` (use 3 ads with distinct `published_at` as in `test_listings_sort.py:30-50`; assert `page_obj` matches `date_desc`). Assert `response.context["current_sort"] == "not_a_real_sort"` (documents the echo-in-URL deviation). No DB-free unit path — the sort branch is inline in the view functions (`listings.py:401-402`, `search.py:207-208`), not a separable symbol.
