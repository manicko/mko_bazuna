# Audit Conclusion: Server Backup Planning Documents

**Audit Date:** 2026-09-01
**Scope:** Audit of `.ai/plans/server_backup/plan.md` (552 lines) and `.ai/plans/server_backup/research.md` (784 lines) against current architecture.
**Sources of current truth:** `current-architecture-report.md` (CA), `research-best-practices-report.md` (BP), the project source tree, `docker-compose*.yml`, `Makefile`, and `docs/ops/restore.md`.
**Confidence:** `FACT` = verified against source code / filesystem / compose files; `INFERENCE` = derived from the current architecture report.

---

## 1. Executive Summary

The two old planning documents are **largely stale**. Of the implementation approach they propose — a custom `docker/Dockerfile.backup` multi-stage image shipping Restic + B2 credentials via Docker Swarm secrets, backed by `scripts/backup.sh`, `scripts/restore.sh`, and `scripts/verify-backup.sh`, with new Makefile targets `backup-prod`/`restore-prod`/`verify-backups`/`media-backup` and a 25-variable `.env.docker.example` — **none of it was implemented**. Filesystem verification confirms that `docker/Dockerfile.backup`, `scripts/backup.sh`, `scripts/restore.sh`, `scripts/verify-backup.sh`, the `secrets/` directory, and `docs/ops/backup-operations.md` all **do not exist**. The only backup code in the repository today is a minimal, pre-existing `postgres:18-alpine` service that runs `pg_dump -F c` on a 7-day local-retention loop with no Restic, no B2, no media backup, no offsite storage, and no verification step.

That said, the **strategic recommendation** — `pg_dump + Restic + Backblaze B2` — **remains valid** per the 2026 best-practices report, which confirms the stack's core paradigm is still correct. The old plans are stale on *execution details and current-system facts*, not on the top-level toolstack direction. The critical discrepancies are: (1) the old plans describe a backup implementation that was never built while the current service is a bare `postgres:18-alpine` image; (2) the old plans assume a 25-variable environment while the real `.env.docker.example` has 73 variables and none of the B2/Restic/Healthcheck variables exist; (3) the old research table of tables lists 9 tables while the current schema has 31, and is missing every GDPR/retention, multi-currency, multi-lingual-FTS, trust-score, and analytics table; (4) the old plans propose Docker Swarm `secrets:` for the Restic password, which the best-practices report explicitly says is not applicable to single-node compose; and (5) the old plans reference a B2 S3 endpoint region and a Restic version that are out of date. The updated plans must therefore rewrite the implementation sections from scratch while preserving the core toolstack recommendation, and must add coverage of all architecture features the old plans never accounted for (Redis, the scheduler service, GHCR pre-built images, the 3-stage Dockerfile, compose project isolation, the sourced-entrypoint pattern, and `Makefile.ps1`).

## 3. Detailed Findings

### 3.1 Architecture (A1–A14)

**The proposed custom backup image was never built.** The old `plan.md` §2.2 proposes `docker/Dockerfile.backup`, a two-stage Alpine image with `restic=0.18.*`, `postgresql-client=18.*`, and `bash`. A direct filesystem search confirms this file does **not exist** — the only Dockerfile present is `docker/Dockerfile` (3-stage: builder → runtime → test-runtime, per CA §1.5). The actual `backup` service in `docker-compose.prod.yml` (lines 65–97) uses `image: postgres:18-alpine` with an inline `/bin/sh -c` loop that runs `pg_dump -F c`, stores to `./backups/dump_YYYYMMDD.dump`, prunes with `find -mtime +7 -delete`, and sleeps 86400. There is no Restic, no B2, no media mount, no verification, and no Restic password anywhere in this service.

**Media volume mount path is wrong.** `plan.md` §2.1 mounts `media_volume:/media:ro` into the backup container and `restore.sh` §3.2 uses `$MEDIA_DIR:-/media`. The current architecture mounts the media volume at `/app/media` in the `web`, `bot`, and `seed` containers (CA §2.1 line 155–157), and at `/media_volume:ro` in `nginx` (CA §2.1 line 158, nginx.conf line 84). The path `/media` does not exist in any current service. Any backup/restore script using `/media` would silently find nothing.

**Docker Swarm secrets are not applicable.** `plan.md` §2.3/2.4 and §3.1/3.3 reference `secrets:` in compose and `secrets/restic_pass.txt` on the filesystem. Neither exists. The best-practices report §6.1 is explicit: for a single-VPS Docker Compose deployment, Docker secrets (Swarm mode) are not applicable; the recommendation is an `env_file` plus a file-mounted `RESTIC_PASSWORD_FILE` at `/opt/mko-bazuna/secrets/restic_repo_key` with `chmod 600`.

**The old plans omitted entire subsystems.** `research.md` §3.1 lists only `nginx, web, bot, postgres` plus optional `pgbouncer/backup/scheduler`. It completely omits **Redis** — now a core service (`redis:7-alpine`, ephemeral, shared cache via `REDIS_URL` for cross-worker rate limiting — CA §2.3). It also omits the **one-shot startup chain** (`db → migrate → load_catalog → create_admin → seed → web/bot`) that runs before any traffic (CA §1.4), the **scheduler** service (hourly GDPR/data-retention sweeps with advisory locks, CA §3.3), the **3-stage Dockerfile**, **GHCR pre-built image pulls** in prod (CA §1.5, §4.5), **compose project isolation** (`mko-bazuna-dev`/`mko-bazuna-test` with distinct named volumes — CA §1.3), the **sourced-entrypoint pattern** (`entrypoint.sh` guards its body with `BASH_SOURCE[0] = $0` — CA §1.6), and **`Makefile.ps1`** for Windows dev (CA §1.3). The updated plans must treat these as prerequisites for any correct backup/restore procedure (e.g., restore must target the right compose project and include `env-file`).

**Accurate elements in the old research.** `research.md` §2.2 (media at `/app/media`, UUID naming, JPEG-only, EXIF stripping), §2.3 (static files reconstructible), §3.2 (volumes), §5.1/5.2 (the minimal current backup service and Makefile targets), §5.3 (the gap list), and §2.1 django-mptt reference are all **VALID** and confirmed by source.

### 3.2 Environment / Secrets (B1–B6)

The environment-variable model has diverged significantly. The old `plan.md` §1.1 defines a 25-line `.env.docker.example` with 14 variables; the current committed template has **73 lines / 23 variables**. The 6 backup-specific variables (`B2_KEY_ID`, `B2_APP_KEY`, `RESTIC_PASSWORD`, `HEALTHCHECK_UUID`, `BACKUP_RETENTION_DAYS`, `BACKUP_RETENTION_WEEKS`) are **absent** from both `.env.docker.example` and the runtime `.env.docker` (CA §4.1, §4.3). The stale 25-line template still exists at `.ai/plans/server_backup/.env.docker.example` and was apparently never merged upstream.

New variables that appeared since the old plans and are **missing** from them: `REDIS_URL`, `BOT_USERNAME`, `SITE_URL`, `IMMEDIATE_ALERTS_ENABLED`, `PLAUSIBLE_HOST`, `SEED_USERS`, `SEED_ADS`, `REGISTRY`, `REPOSITORY`, `IMAGE_TAG`, `FIX_PERMISSIONS`, `SKIP_ENV_CHECK`, `DEBUG`, `ALLOWED_HOSTS`. Several of these are operationally relevant to backup/restore: `REGISTRY`/`REPOSITORY`/`IMAGE_TAG` govern which GHCR image the `backup`/`scheduler` services pull in prod (CA §4.5); `SEED_USERS`/`SEED_ADS` define the restore-then-resume workflow; `REDIS_URL` means a full DR rebuild must also provision Redis.

The old defaults are also wrong: `plan.md` defaults to `POSTGRES_DB=postgres` / `POSTGRES_USER=postgres`, while the current env uses `bazuna_db` / `bazuna_user` (CA §4.1), and restore.md's manual example hard-codes `postgres`/`postgres` (CA §5.5 line 573) — itself flagged as a docs bug.

### 3.3 Database Scope (C1–C10)

The old `research.md` §2.1 lists **9 tables**; the current schema has **31 tables** (CA §6.1). The 22 unaccounted tables span every subsystem: GDPR (`consent_records`), multi-currency (`exchange_rates`), category navigation (`category_paths`, `category_listing_purposes/features/conditions`), reference data (`lookup_groups`, `lookup_items`), analytics (`daily_ad_metrics`, `popular_searches`, `search_history`), buyer engagement (`saved_searches`, `ad_favorites`, `saved_search_notifications`), seller reputation (`seller_trust_scores`, `seller_verifications`), and moderation (`ad_moderation_priorities`).

Specific field-level staleness: the `ads` table gained `title_ru/en/bs`, `description_ru/en/bs`, `price_amount`, `price_currency`, `price_normalized_eur`, three language-specific search vectors (`_ru`/`_en`/`_bs`), `published_by`, `moderated_by`, `moderation_failed_at`, `rejected_at` — none in the old table. `ad_images` gained `sha256`. `analytics_events` gained a `source` column. The moderation audit table is now named `moderatoractionlog` (not `moderation_action_logs`).

**PII scope expanded substantially.** Beyond `users.telegram_id`, the current schema stores `users.chat_id`, `users.username`, `saved_searches.unsubscribe_token` (a 32-char capability token enabling anonymous unsubscribe), `consent_records.ip_address`/`user_agent` (anonymous-only, nullable), and `seller_verifications.phone_number` (CA §6.2). A full-DB `pg_dump` therefore contains more PII classes than the old plans model, with different erasure semantics.

**GDPR retention machinery is undocumented in old plans.** `research.md` mentions `consent_given_at`/`consent_revoked_at` but never describes the four scheduler sweeps (30-day `consent_hard_delete` L3, 120-day `purge_deleted_ads` L11, 90-day `purge_rejected_ads` L7, 7-day `purge_failed_ads` L6), each gated by PostgreSQL advisory locks and run hourly by the `scheduler` service (CA §3.3, §6.3). The consent audit trail is append-only (a withdrawal writes a *new* row) — a detail with backup/restore implications (partial-table restore must preserve history). This is a **gap**, not a staleness: the old plans predate the GDPR retention subsystem.

### 3.4 Backup / Restore Procedures (D1–D10)

**Every proposed script and Makefile target is absent.** `plan.md` §3.1/3.2/3.3 specify `scripts/backup.sh`, `scripts/restore.sh`, `scripts/verify-backup.sh`; filesystem search confirms all three are absent. `plan.md` §4.1 proposes `backup-prod`, `restore-prod`, `verify-backups`, `media-backup` Makefile targets; the current Makefile (CA §5.2) has only `backup`, `restore`, `prune-backups`. `plan.md` §5.1/5.2 intend to extend `docs/ops/restore.md` with media/Restic/offsite sections and to create `docs/ops/backup-operations.md`; `restore.md` exists (176 lines) but contains **none** of those sections, and `backup-operations.md` does not exist.

**The restore runbook has a latent bug.** `restore.md` §Option A hard-codes `pg_restore -U postgres -d postgres` and the Troubleshooting section says "The default is `postgres`", but the runtime `.env.docker` uses `bazuna_user`/`bazuna_db` (CA §5.5 line 573). The old `restore.sh` also stops services via `docker-compose.yml` (root only), which would miss prod overrides — the correct invocation is `docker compose -f docker-compose.yml -f docker-compose.prod.yml ...`.

**The `media-backup` target references a non-existent volume name.** `plan.md` §4.1 `media-backup` uses `docker run --rm -v mko_bazuna_media_volume:/media`, but the actual volume is named `media_volume` and is project-prefixed (e.g., `mko-bazuna-dev_media_volume`) — so the old volume name is doubly wrong.

### 3.5 Tooling (E1–E7)

The **core toolstack recommendation survives** (`pg_dump + Restic + Backblaze B2` — BP Executive Summary), but three specifics are out of date:

1. **Restic version:** old plans specify 0.18; BP §4.1 confirms v0.19.1 is current (released 2026-07-05).
2. **B2 backend:** old plans use the native `b2:` scheme; BP §3.3 confirms the native B2 backend is **deprecated in Restic 0.19.0** and the `s3:` scheme pointing at `s3.us-west-002.backblazeb2.com` is now required. `research.md` §12.7 already uses the S3 gateway (good direction) but with region `us-west-004` instead of the recommended `us-west-002`.
3. **pg_dump flags:** the old `backup.sh` §3.1 runs bare `pg_dump -F c`; BP §1.2 recommends `--format=custom --jobs=4 --no-owner --no-privileges --if-exists --clean` for parallel, idempotent, permission-safe restores on PostgreSQL 18.

**MinIO is dead.** `research.md` §11.4 lists MinIO as a viable S3 alternative and notes "Archived Feb 2026 — DO NOT use." The best-practices report §3.2 is definitive: the GitHub repo was archived 2026-04-25, pre-built binaries halted October 2025, admin UI removed May 2025. Successor self-hosted S3 projects are SeaweedFS S3, Garage, RustFS, and Ceph RGW (BP §3.2). `research.md`'s contradictory framing ("viable" + "do not use") must be resolved.

The retention-forget pattern (`restic forget --keep-daily 7 --keep-weekly 4 --prune` — research.md §12.7/§12.2) is conceptually correct but should be refined to BP §4.1's `--keep-daily 7 --keep-weekly 4 --keep-monthly 12 --keep-yearly 3 --prune`, paired with a weekly `restic check --read-data-subset=1/7` deep check.

### 3.6 Security & Compliance (F1–F6, G5–G6)

**Media backup is entirely absent.** A full DB dump preserves ad metadata, but the actual ad photos (the platform's largest value store, ~200 GB) live only in `media_volume`, which the current backup service does not mount (CA §5.1). `research.md` §5.3 correctly flags "No media backup" as a gap; the old `plan.md` §2.1's `/media` mount and `media-backup` target were never realized.

**Secrets management pattern is wrong for this deployment.** `plan.md` §2.3/2.4 proposes Docker Swarm `secrets:`. BP §6.1 makes clear this is inapplicable to single-node compose: the correct pattern is an env_file variable referencing a file-mounted key (`RESTIC_PASSWORD_FILE=/run/secrets/restic_repo_key`) on the host, plus a dedicated least-privilege B2 application key scoped to the backup bucket (BP §8.3).

**Encryption coverage is incomplete.** The old plans rely on Restic's AES-256 client-side encryption (still valid — BP §8.1) but omit B2 **SSE-S3** server-side encryption, which BP §8.2 recommends as a defense-in-depth layer against repository-password compromise.

**Healthchecks.io endpoint is inconsistent.** `research.md` §12.7/§12.2 uses `hc.pfelya` / `hc.pfelya`; BP §7.3 confirms the canonical public API is `hc-ping.com` and that `hc-pfyela.com` is plausibly a self-hosted instance. The updated plan must either standardize on `hc-ping.com` or explicitly document the self-hosted URL and how to swap it.

**No backup testing in CI.** BP §7.3 and CA §7.3 confirm: CI uses an ephemeral `postgres:18-alpine` service container and has no backup-related env vars, no `secrets/`, and no Restic/B2 references. Any backup implementation must be validated manually (e.g., a DR restore dry-run), not via CI.

### 3.7 Compose Project & Deployment Model (G1–G4)

The old plans assume a single root `docker-compose.yml` with no project-name scoping. The current architecture (CA §1.3) uses **GNU Make target-specific `COMPOSE_PROJECT_NAME` exports** (`mko-bazuna-dev` vs `mko-bazuna-test`), reflected identically in `Makefile.ps1` (CA §1.3), so volume names, container names, and network scopes are all project-prefixed. Production deployment (CA §1.4) requires `docker compose --env-file .env.docker -f docker-compose.yml -f docker-compose.prod.yml up -d` followed by a separate `docker compose run --rm migrate` — a startup ordering the old `restore.sh` (which calls `docker compose stop web bot` against the root compose only) would not reproduce. Restore procedures must therefore include the correct `--env-file` and compose file merge.

---

## 4. Conclusion

**What the old plans got right:** The strategic toolstack recommendation — `pg_dump` (logical backup) + Restic (deduplicating archive) + Backblaze B2 (low-cost offsite) — remains the correct 2026 approach (BP Executive Summary, §1.1–§1.2). The core concept of a full-DB `pg_dump -F c` daily backup with retention pruning is sound. The old plans correctly identified the two critical data assets (PostgreSQL database + `media_volume`), correctly classified static files and source code as git-reconstructible (non-backup-critical), correctly flagged media backup and offsite storage as the central gaps, and accurately described the *current minimal* backup service and Makefile targets as they existed (research.md §5.1–§5.3). Media handling details (UUID v4 naming, JPEG-only with magic-byte validation, EXIF stripping, EXIF-stripped thumbnails) and the django-mptt category model are also accurate.

**What is critically wrong or stale:** The implementation was **never executed** — every artifact the plan proposed (`Dockerfile.backup`, `scripts/backup.sh`, `scripts/restore.sh`, `scripts/verify-backup.sh`, `secrets/` directory, `docs/ops/backup-operations.md`, the four new Makefile targets) is absent from the filesystem, and every backup/Restic/B2 environment variable (`B2_KEY_ID`, `RESTIC_PASSWORD`, etc.) is absent from the real env files. The backup service that *does* exist is a bare `postgres:18-alpine` container with no Restic, no encryption, no media mount, and no verification — a far cry from the plan's vision. The plan's Docker secrets pattern is inapplicable to single-node compose (Swarm-only). The restore runbook in `docs/ops/restore.md` contains a hard-coded `postgres`/`postgres` mismatch with the actual `bazuna_user`/`bazuna_db` credentials. The media volume mount path `/media` is wrong in every script that references it. The Restic version (0.18) and B2 S3 endpoint region (`us-west-004`) are out of date. MinIO is referenced as viable when it was archived in April 2026.

**What the updated plans must address:** The updated `plan_updated.md` and `research_updated.md` must (a) acknowledge that the old implementation spec was never built and rewrite the implementation against the *actual* current state — a `postgres:18-alpine` backup service whose incremental upgrade path to Restic + B2 adds the custom image, the scripts, and the env vars as *new* work rather than assumed-existing; (b) replace the Docker Swarm `secrets:` pattern with the BP-recommended file-mounted `RESTIC_PASSWORD_FILE` + env_file approach; (c) correct the media mount path to `/app/media` (and explicitly mount `media_volume` in any media-backup service, which the current service omits entirely); (d) adopt Restic v0.19.1, the `s3:` B2 S3-gateway backend at `s3.us-west-002.backblazeb2.com`, and the BP-recommended pg_dump flags (`--format=custom --jobs=4 --no-owner --no-privileges --if-exists --clean`); (e) adopt the refined retention policy (`--keep-daily 7 --keep-weekly 4 --keep-monthly 12 --keep-yearly 3 --prune`) with weekly `restic check --read-data-subset`; (d) correct the restore.md `postgres`/`postgres` bug and add the missing media-restore, Restic-restore, and offsite-recovery sections; (e) expand the database scope to all 31 current tables and the full GDPR/retention sweep picture (four advisory-locked scheduler sweeps, 30-day consent hard-delete, 120-day deleted-ad purge); (f) expand PII coverage to include `unsubscribe_token`, `consent_records.ip_address`/`user_agent`, `seller_verifications.phone_number`, `users.chat_id`/`username`; (g) retire all MinIO references and document SeaweedFS S3 / Ceph RGW / Garage / RustFS as successors; (h) add B2 SSE-S3 bucket encryption as a defense-in-depth layer; and (i) account for compose project isolation (`mko-bazuna-dev`/`mko-bazuna-test`), GHCR image overrides, the sourced-entrypoint pattern, the 3-stage Dockerfile, and `Makefile.ps1` as prerequisites for any correct backup/restore/DR procedure. The core paradigm needs no change; the execution must be rebuilt from the current baseline.
